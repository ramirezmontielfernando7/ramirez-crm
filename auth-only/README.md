# Backend auth-only · preparación local, no arrancado

Base exacta: 0b611126717ede5dca0f4ea766f28b99befd648c. Worktree independiente /workspace/work/dashfort-auth-offline, rama codex/dashfort-auth-offline-20261119. No es un servidor activo ni una imagen lista para desplegar. No ejecutar pnpm start, next dev/start, scripts/migrate.mjs, Docker o PostgreSQL.

`handler.mjs` es una fábrica Request/Response sin listener: admite únicamente tres rutas Better Auth con método exacto, origen exacto, cuerpo limitado, identidad de ambas conexiones y errores sanitizados. Los tests usan dobles de memoria. `existing-auth.ts` prepara la reutilización perezosa de getAuth existente; no inventa cookies ni endpoints. Solo ese adaptador podría consultar las dos conexiones después de una futura invocación autorizada. No se ejecutó ni se probó con dependencias backend/BD reales.

`policy.mjs` rechaza entorno heredado, tokens de proveedores, DSN de migración, hosts/bases/roles distintos y perfiles ambiguos. El plan válido devuelve readyToStart:false. La comparación de identidad exige BD, rol, privilegios, PostgreSQL 18 e identificador nuevo de instancia. La identidad debe obtenerse de consultas reales del adaptador después de autorización; no sustituirlas por un JSON manual. Una variable o `.invalid` no prueba firewall/red.

`environment.example.json` contiene placeholders deliberadamente no operativos. No generamos secretos reales. El esquema existente de getEnv requiere ENCRYPTION_KEY y verify token; el token test está fijado a una muestra sin proveedor. Se mantiene el rol vocero_app/vocero_system en una instancia totalmente nueva para preservar compatibilidad con SQL existente. El plan de migración separado usa i2p_migrate: 0026 necesita privilegios de administrador de clúster para crear BYPASSRLS, por lo que esa credencial solo pertenecerá al job de migración test y nunca al runtime. Revisar ese privilegio antes de ejecutar, sin editar migraciones originales.

`network-plan.json` es una especificación, no reglas aplicadas. Requiere otro host local, red interna, DNS solo interno, egress IPv4/IPv6 denegado, cero mounts de host/.env/.aws, cero sockets Docker, volumen nuevo y BD sin puerto publicado. No se genera compose ejecutable para evitar confundir una plantilla declarativa con aislamiento acreditado. Preparar firewall y configuración efectiva será una operación revisada y autorizada, no se activa aquí.

Se añade un guard puro a instrumentation antes del primer import operativo y al migrador antes de resolver DSN/crear cliente: bloquea presencia de marcadores test, host o BD test. El arranque normal sin esos marcadores conserva su camino; requiere validación de build backend y revisión del entorno efectivo antes de cualquier fusión. No se modifica Dockerfile, comandos start, hooks de auth ni migraciones SQL. Los scripts originales de migración quedan bloqueados para el perfil test: un procedimiento test autorizado separado sigue pendiente. El perfil propuesto elude el arranque completo de Next mediante una entrada dedicada. prepare-node.ts contiene una fábrica Node con el adaptador oficial better-auth/node; no se invoca ni llama a listen. Su compatibilidad de tipos/protocolo sigue pendiente de resolver dependencias backend y de autorización operativa. Así no importa instrumentation/workers. Las pruebas comprueban rutas rechazadas antes de importar auth, preservación de Set-Cookie con dobles y bloqueo ante identidad desconocida. No acreditan todos los imports transitivos del auth real: revisar con sus dependencias resueltas y pruebas con stubs antes de una ejecución.

Compatibilidad futura: tsconfig/ESLint/.dockerignore excluyen Mobile y auth-only. No hay merge. Las pruebas de exclusión son estáticas; el build/lint completo del main requiere dependencias backend que no instalamos. No activar CI ni asumir que un análisis de cadenas acredita un grafo transitivo completo.

Puerta de seguridad: review de Claude + autorización del propietario antes de generar secretos, crear red/volumen/BD, configurar identidad de instancia, migrar, proveer listener o invocar el adaptador contra BD. Más tarde revisar cookie jar/rotación/CSRF/TLS/nativo y bootstrap de permisos de sesión. El plugin org sigue cerrado; no habilitarlo para satisfacer el simulador.

Reversión: no hay servicios que detener ni BD que borrar en esta entrega. Conservar rama/commits/bundle; descartar únicamente este worktree tras respaldarlo si se decide no usarlo. Futuro rollback: detener solo proyecto test, revocar solo credenciales test; destruir un volumen exige verificar IDs y autorización. Producción permanece fuera de estas operaciones.
